# Project Context & Operational Rules — JS Dojo

## 1. Core Knowledge Base (프로젝트 필수 참조 문서)
작업 지시를 받거나 시스템을 분석할 때, 아래 문서를 최우선으로 열람하고 규약을 준수한다.
- **프로젝트 헌법:** `CLAUDE.md` — 목적·디렉터리 계약·검증 기준
- **콘텐츠 계약 스키마:** `content/schema.json` — 챕터/스텝 YAML 계약 (JSON Schema 2020-12)
- **학습자·작성자 가이드:** `README.md`
- **엔진 원본:** [codedojo](https://github.com/ssj37v/codedojo) — 엔진은 같고 콘텐츠만 다르다. `dojo/` 변경은 양쪽 모두에 타당한지 먼저 따진다

## 2. Operational Directives (Non-Negotiable)
이 규칙들은 프로젝트의 헌법이며 절대적으로 준수한다.

### R00: COMPLEXITY_TIERING (작업 복잡도 분류)
작업 지시를 받으면 아래 기준으로 복잡도를 **먼저** 판정하고, 해당 티어의 프로세스만 실행한다.

| 티어 | 기준 (모두 충족) | 적용 프로세스 |
|------|-----------------|--------------|
| **Trivial** | 수정 파일 1개 AND 변경 ≤30줄 AND 검증기·콘텐츠 무관 | 직접 수정 → 완료 보고. Plan Mode·Chunk·code-reviewer·사후 리포트 생략 |
| **Simple** | 수정 파일 ≤3개 AND 단일 모듈 AND 검증기·콘텐츠 무관 | 간략 계획 텍스트 출력 → 실행 → 완료 보고 |
| **Standard** | 위 조건 미충족 OR 검증기 변경 OR 콘텐츠·스키마 변경 OR 학습자 자산 조작 OR 다중 모듈 | Phase 0~3 전체 파이프라인 실행 |

#### 불변 규칙 (티어 무관, 항상 적용)
- R02 (학습자 자산 보호), R03 (교차 검증), R09 (교착 탈출), R10 (검증 후 시도), **R13 (검증 정직성)**

#### 승격 규칙
- 작업 중 영향 범위가 초기 판정보다 넓어지거나 **판정 경로(`dojo/verify/`)·콘텐츠 스키마·학습자 파일 조작(`scenario.mjs`, `--reset`)에 닿으면** 즉시 Standard로 승격한다.
- 사용자가 `/plan`을 명시하면 무조건 Standard로 취급한다.

### R01: PLANNING_ENFORCEMENT (계획 우선 원칙)
- **계획 우선**: Standard 티어 작업 시 코딩 전 반드시 Plan Mode로 기획 및 Chunk 분해 후 승인받는다.
- **문서 동기화**: 콘텐츠 스키마·CLI 인터페이스·검증기 계약 변경 시 `CLAUDE.md` 및 `README.md` 업데이트를 필수 프로세스로 강제한다.

### R02: LEARNER_ASSET_SAFEGUARD (학습자 자산 보호 규정)
보호 대상은 **학습자가 손으로 쌓아 올린 결과물**이다. 이것을 잃으면 학습 동기 자체가 무너진다.
- **workspace 불가침:** `workspace/`와 그 git 이력은 학습자 소유다. 엔진이 이를 삭제·덮어쓰기·강제 커밋하려면 반드시 명시적 확인 프롬프트를 거친다.
- **경로 봉쇄:** 파일을 삭제·변형하는 모든 코드는 대상 경로가 프로젝트 루트 하위인지 먼저 검사한다. 상위 경로 탈출(`..`)·심볼릭 링크·절대경로 주입을 거부한다.
- **진도 파일 보존:** `.dojo/progress.json`은 원자적 쓰기(임시 파일 → rename)로만 갱신한다. 파싱 실패 시 덮어쓰지 말고 백업 후 보고한다.
- **콘텐츠 무결성:** `content/*.yaml`은 정답·힌트·검증 기준의 단일 출처다. 변경 시 반드시 **"오답이 통과되지 않는다"는 회귀 테스트를 동반**한다.

### R03: SIDE_EFFECT_MITIGATION (기존 코드 훼손 방지)
- 코드를 수정/삭제하기 전, 해당 모듈을 참조(import/호출)하는 다른 시스템이 있는지 반드시 `Grep`으로 교차 검증하여 부작용 범위를 파악한다.
- 특히 `content/schema.json`(콘텐츠 계약), `dojo/verify/index.mjs`(체크 타입 디스패치), `progress.mjs`(저장 포맷)는 다중 소비자를 가지므로 변경 전 소비 지점을 전수 확인한다.

### R04: PROACTIVE_RISK_MANAGEMENT (리스크 주도적 대안 제시)
- 병목·보안 취약점·비효율이 발견되면 단순 경고에 그치지 않고, 기술적 트레이드오프가 분석된 **'권장 옵션(Recommended Options)'**을 제시한다.
- **신규 npm dependency 추가**는 학습자의 설치 부담과 버전 드리프트 위험을 늘리므로 항상 R04 대상이다 — 무의존 대안을 우선 검토하고 근거와 함께 제안한다.

### R05: Q&A_ISOLATION (질문 답변 격리 원칙)
- 단순 질문(개념·의견 등)에는 오직 답변만 수행하고 즉시 종료한다. 불필요한 코드 수정이나 다음 단계 제안을 금지한다.

### R06: SUB_AGENT_DISPATCH (서브에이전트 디스패치 원칙)
각 에이전트는 독립 컨텍스트에서 실행되므로 분석과 실행을 분리할 때 사용한다.

#### 자동 디스패치 에이전트 (필수)
- **investigator** — 버그, 검증기 오탐/미탐, 진도 유실, 플랫폼별 spawn 실패 등 원인 불명 현상 발생 시 코드 수정 **전** 선행 실행.
- **code-reviewer** — **검증기·콘텐츠 스키마·학습자 파일 조작·다중 모듈**을 건드린 Chunk에만 완료 직후 자동 실행하여 사이드이펙트를 검증한다. 단일 파일 저위험 변경(문서·설정 한 줄)은 생략한다.

### R07: MODEL_TIERING (모델 티어링 원칙)
서브에이전트 디스패치 시 복잡도에 따라 `model`을 명시한다: **opus**(학습 설계·판정 로직 근본원인·다중모듈) / **sonnet**(탐색·수정·테스트·검증) / **haiku**(리뷰·정리·문서패치·사전수집). 모호하면 sonnet 기본값.
- **상세 매핑표 → `.claude/rules/playbooks.md` (R07)**

### R08: CONTEXT_MAP_FIRST (컨텍스트 맵 우선 참조 원칙)
모듈 수준 작업을 시작할 때, 코드 전면 탐색(Explore) **전에** 다음을 따른다:
1. **계약 우선:** 콘텐츠 관련이면 `content/schema.json`을, 구조 관련이면 `CLAUDE.md`의 디렉터리 계약 표를 먼저 Read한다.
2. **판정 경로 확인:** 통과/실패 동작이 관련되면 `dojo/verify/index.mjs`의 체크 타입 디스패치를 먼저 확인한다.
3. **그다음:** 필요한 파일만 직접 Read한다. `dojo/`는 파일당 소규모이므로 대상 모듈을 직접 여는 것이 효율적이다.

### R09: DEADLOCK_ESCAPE (교착상태 탈출 프로토콜) — 불변
동일 접근법이 반복 실패(같은 에러 **2회**, 수정→실패 **3회**, 서로 다른 접근법 **2개 이상** 실패)하면 교착으로 판정하고 **RECITE-PIVOT**(목표 복창 → 원인 요약 → 전환: 접근법 변경 / investigator 디스패치 / 사용자 보고)으로 즉시 탈출한다.
- **금지:** 매개변수만 바꿔 3회 이상 재시도, sleep 후 동일 시도 반복, 에러 무시 후 진행.
- **상세 → `.claude/rules/playbooks.md` (R09)**

### R10: EFFICIENT_DEBUGGING (효율적 디버깅 및 병목 방지 원칙)
1. **Verify-Before-Try:** 함수 시그니처, 콘텐츠 필드명, CLI 플래그, 외부 명령 인자를 **추측하지 않는다.** 반드시 소스(`content/schema.json`, `dojo/verify/index.mjs`, `dojo/cli.mjs`)를 Read로 확인한 후에만 호출/테스트한다.
2. **CLI 우회 및 직접 호출:** 판정 로직 검증 시 대화형 입력을 배제하고 대상 모듈(`verify/*`, `fade.mjs`, `progress.mjs`)을 `node --test`에서 직접 `import`하여 실행한다.
3. **런타임 준수:** Node 22+ 기준으로 실행한다. 테스트는 `node --test`(=`npm test`)를 사용하고, 임의 전역 도구·미승인 dependency에 의존하지 않는다.
4. **플랫폼 확인:** 외부 명령 실행 코드는 Windows에서 실제로 돌려 확인한다. `npm`/`npx`는 Windows에서 `.cmd` shim이므로 POSIX 가정으로 작성하지 않는다.

### R12: SCRIPTS_LIFECYCLE (임시 산출물 격리 원칙)
- **저장소 루트나 `dojo/`에 임시 디버깅 파일을 만들지 않는다.** 임시 산출물은 세션 scratchpad 디렉터리를 사용한다.
- 반복 실행이 필요한 운영 스크립트만 `scripts/`에 두고, 파일 상단에 `// lifecycle: ops`를 명시한다.
- `workspace/`와 `.dojo/`는 학습자 영역이므로 어떤 임시 파일도 여기에 두지 않는다.

### R13: LEARNING_INTEGRITY (검증 정직성 우선 — 트리플 렌즈) — 불변
이 프로젝트의 존재 이유는 **학습자가 실제로 해낸 것만 통과시키는 정직한 피드백**이다. 통과 판정이 무너지면 튜토리얼 전체가 무의미해진다.

#### 트리거 게이트 (해당 시 자동 발동 + Standard 승격)
`dojo/verify/*` 판정 로직, `content/schema.json`, 챕터 YAML의 `verify`/`hints`/`fade` 블록, `progress.mjs` 저장 포맷, `fade.mjs` 승강등 규칙, `scenario.mjs`의 학습자 저장소 변형, `--reset` 등 파괴적 CLI 플래그 중 **하나라도** 건드리는 변경.
- **제외:** Trivial/Simple 문서·터미널 문구·순수 표현 계층 — R13 생략.

#### 발동 시 트리플 렌즈 복창 (Phase 0에서 의무)
각 렌즈는 서술이 아니라 **실행 가능한 권장 옵션(R04 연계)** + **대응 회귀 테스트**로 귀결되어야 한다.

1. **판정 정직성:** 학습자가 목표를 실제로 달성하지 않고 통과할 경로가 새로 생기는가? 정답 문자열만 베껴 넣기·검증 대상 파일 우회·테스트 무력화가 잡히는가? 판정이 학습자 자기신고가 아니라 **실제 파일 내용·exit code·git 상태**에 근거하는가?
2. **학습자 자산 안전:** 이 변경이 `workspace/`나 git 이력을 지우거나 덮어쓸 수 있는가? 파괴적 동작 전에 확인 프롬프트와 경로 봉쇄가 있는가? 진도 파일이 손상돼도 복구 가능한가?
3. **학습 설계 정합성:** 3단 페이드·힌트 지연·간격반복이 의도대로 작동하는가? 힌트가 너무 일찍 정답을 노출하지 않는가? 난이도 승강등이 학습자를 좌절 구간이나 지루함 구간에 가두지 않는가?

#### 귀결 (필수)
- 새 우회 경로가 생기면 반드시 `test/`에 **"오답·우회 시도가 통과되지 않는다"** 회귀 테스트로 귀결시키고 `npm test`로 확인한다.
- **Stop condition**(false pass 재현·학습자 workspace 유실·진도 파일 손상) 중 하나라도 재현되면 즉시 STOP 후 사용자 보고한다.

## 3. Interaction Workflow (Tiered Pipeline)
**R00에서 판정된 티어**에 따라 선택적으로 실행한다.
- **Trivial/Simple:** Phase 0의 목표 복창만 수행 후 바로 실행. Phase 1~3 생략.
- **Standard:** 아래 Phase 0~3 전체를 엄격히 준수한다.

### Phase 0: Goal Alignment
1. **목표 복창:** 이해한 최종 목표를 간략히 요약 출력한다. (모호하면 STOP 후 역질문)
2. **R13 트리거 점검:** 검증 정직성 트리거에 해당하면 R13을 발동하여 트리플 렌즈(판정 정직성·학습자 자산·학습 설계)로 복창한다.

### Phase 1: Planning & Chunk Breakdown (Plan Mode)
1. **기획:** 배경, 요구사항, 판정·학습 설계 영향, 리스크 분석 및 권장 옵션
2. **Chunk 분해:** 환각 방지와 기존 코드 보호를 위해 가장 보수적인 최소 단위로 분리(Chunk 1, 2…). 각 Chunk는 독립 실행·검증 가능해야 한다.
3. **승인 대기:** ExitPlanMode 호출.

### Phase 2: Chunk-by-Chunk Execution (승인 후)
1. **Execute:** 기존 의존성을 보호하며 Chunk 코드를 작성한다.
2. **Per-Chunk Verification (조건부):** Chunk가 검증기·콘텐츠 스키마·CLI 인터페이스·다중 모듈을 건드린 경우에만 `code-reviewer`를 실행한다. 저위험 단일 파일 변경은 생략한다.
3. **Sync Docs:** 스키마·CLI·검증기 계약 변경 시 `CLAUDE.md`·`README.md`를 즉각 업데이트한다.

#### Chunk 실패 시 롤백 규칙
- Chunk N 실행 중 오류 발생 시 해당 Chunk 변경을 되돌리고 사용자에게 보고한다. 다음 Chunk로 넘어가지 않는다.

### Phase 3: Final Verification (자동 사후 검증)
모든 Chunk 완료 시, 묻지 않아도 아래 포맷으로 리포트를 출력한다.

**[사후 검증 리포트]**
> - **Cross-Module Impact:** [영향을 받는 모듈 나열]
> - **Safeguards Applied:** [로직 훼손 방어 조치 요약]
> - **Learning-Integrity Check:** [R13 발동 시 — 판정 정직성/학습자 자산/학습 설계 3렌즈별 확인 결과 및 실행한 회귀 테스트]
> - **Edge Case Warning:** [실패 가능한 예외 상황 및 처리 상태]
